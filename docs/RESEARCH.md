**Historical planting-only mission (superseded by the user's explicit rescue-first clarification):** cooperative rice stand-gap survey, map and physical seed placement. The current research priority is **risk-aware physical peer recovery and optional offline pooled inference** in this fieldwork context; see [RESCUE_EDGE_RESEARCH](RESCUE_EDGE_RESEARCH.md), [SWARM_EDGE_PLAN](SWARM_EDGE_PLAN.md) and D-0009. **Current strongest comparisons:**
- [IRRI, Rice Production Manual, Plant Establishment](https://www.knowledgebank.irri.org/images/docs/planting-establishment.pdf): target population depends on seedbed, sowing technique, depth, seed quality and variety. This argues against treating every gap as a seed opportunity without crop-stage/context.
- [Nguyen et al., Computers and Electronics in Agriculture (2025)](https://www.sciencedirect.com/science/article/pii/S0168169925010385): robot + RF + handheld soil probes with Gaussian-process spatial moisture fusion. **Prior art**, not our novelty; authors report 97% autonomous robot sampling in their experiments. Don't import their field numbers into this simulation.
- [Roberts-Elliott et al., Robotics (2025)](https://www.mdpi.com/2218-6581/14/6/77): active Kriging-variance-informed multi-robot soil mapping, task allocation and route planning already published. **Shared-map routing alone is not new**; our distinct claim must involve *embodied seed placement, changing-site decisions and measurable cost/quality trade-offs*, compared against this strong family of deterministic methods.
- [NVIDIA Isaac Sim official requirements (5.1)](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/requirements.html): 32 GB workstation RAM / 16 GB VRAM minimum; teammates' reported 8 GB-VRAM laptops cannot be treated as verified compatible. [Official Isaac Sim physics raycast sensors](https://docs.isaacsim.omniverse.nvidia.com/latest/sensors/isaacsim_sensors_physics_raycast.html) are a suitable low-complexity initial obstacle sensor. Actual installation/version pin and host performance require a real test. The same version may expose distinct module namespaces; don't paste version-ambiguous imports.

**Research/test plan:** sample sparse local moisture/firmness and vegetation-gap proxies with explicit measurement radius/noise, fuse shared map with uncertainty, choose whether information gain or planting is worth travel, assign two robots safe routes, physically release a rigid-body seed proxy, then independently score landings against hidden synthetic quality. Compare grid seeding, capable deterministic map-guided planner and optional model-driven investigator on identical worlds and cost budgets. Check if conventional approach wins in uniform plots. Do **not** claim tree/rice survival, yield, flooding prevention, learned soil analytics or real autonomous field deployment.

## Real-world win discipline

- **Usefulness:** name one concrete beneficiary and action they would choose to use, not a fictional persona.
- **Differentiation:** explicitly test a strong alternative: deterministic controller, existing product, model without tools, or standard optimiser. An LLM pasted into UI is not novelty.
- **Surprise and depth:** demonstrate an uncertain/novel case where the system decides what to do, not a canned prompt-response.
- **Reliability:** preserve denominator, failed cases, latency, environment and test instructions; never cherry-pick one lucky run.
- **Narrative:** problem → physical/simulated action → independently verified result → edge case → honest limitations. Show code execution before polishing pitch slides.

Research for product prior art belongs in current `docs/PRODUCT.md` (claim and nearest baseline) and source references here if extensive; avoid creating large shadow dossiers in this public repository.

| [System Switch](https://arxiv.org/abs/2610.09683) (7 Oct) | Selective fast-to-slow handoff helps some offline decisions, but **no evaluated variant completed the end-to-end closed-loop Doom mission** in 33 games. | Offline decision accuracy must be measured against *mission completion*; confidence alone is not a success signal. |
| [RobotAgentBench](https://arxiv.org/abs/2610.34649) (26 Oct) | Realistic simulated household layout benchmark separating manipulation, contextual reasoning, failure recovery, and overall mission completion. | Judge and compare an actual changing-world episode, not a plausible failure explanation or static simulated picture. |
| [EmbodiedLab](https://arxiv.org/abs/2610.35385) (26 Oct) | Hidden physical state requires the robot to choose information-gathering actions and then act. | Test **act to learn before doing**, while comparing Bayesian active sensing and standard system identification. |

**Architectural hypothesis, not a requirement:** simulate **sensors → state/uncertainty → local bounded policy/controller**; at unexpected ambiguity or verified failure, optionally call a **bounded supervisory investigator** to select *a physical probe or high-level recovery plan*. All proposals pass deterministic action limits. Continue safe core control while slow reasoning is absent or unavailable. Typed System One models such as Jev are not automatically local models. A simulator running on a cloud GPU is distinct from a policy requiring cloud inference every step.

**Falsifiable implementation gate:** Before any model/API commitment, obtain a reproducible moving robot with one genuine simulated sensor, observable action feedback and independent scoring. Test a **nominal scenario and one altered same-episode scenario** (sensor noise, new obstacle, moved target or changed friction). Keep the hidden simulator fault separate from agent-facing observations; preserve a controlled seed and continuous <=60-second perception/action video. Compare at least (1) fixed trajectory, (2) competent **reactive deterministic replanner / finite-state controller**, and (3) proposed decision component; for physical uncertainty also compare Bayesian active sensing/system identification. Add an ablation (4) optional slow reasoning, recording completion, harm, recovery delay, additional probes, slow-call frequency, p95 latency and no-network fallback. **If the simple baseline matches the proposed model, do not claim AI necessity.**

### Role-routing experiment (not yet executed)

1. **Integrator/programmer** — ChatGPT connected to GitHub can inspect, change code in its owned branch and review PRs; it cannot by itself run teammate-local Gemini CLI or certify simulation runtime tests. Human retains project authority, model/spend approval and merge control.
2. **Specialist coding worker** — use a human-started Gemini CLI session (3.8 Flash proposed for bounded tasks) with narrow files, a base SHA, exclusive owned paths, a fixture and a passing criterion. A second CLI session needs another worktree/branch. Do not confuse an API model ID with a CLI install/entitlement.
3. **Complex investigation** — use Gemini 4 Argon only if the first pass encounters ambiguous causal debugging, significant cross-module reasoning or long-horizon code synthesis. Compare its results with a smaller model or deterministic approach when feasible.
4. **Independent reviewer** — a separate read-only Gemini subagent or a human checks the exact PR, valid/invalid fixtures, claimed results and user-value evidence. Do not let an implementing agent redefine the success metric or change the baseline after seeing failure.
5. **Robot runtime** — for a chosen project, control-rate physics/motor behaviour belongs to a deterministic/specialised controller. Models such as Gemma 4 (only if actual offline weights/hardware are verified), Jev or a frontier Gemini may earn a narrowly scoped *deliberation* job when measured; none is required just because it was presented. Voice/image/video media models have no default role.

**Allocation test once work exists:** sample 2–3 real independent development tasks; log exact model/client and access, pass/fail on predeclared checks, new defects caught by review, integration rework, elapsed time and tokens/monetary cost *where actually observable*. Compare a single-worker path with parallel workers on comparable tasks. Do not force statistical claims from a hackathon-sized sample. If parallelism or a skill costs more and introduces integration errors without improving outcomes, stop using it.

**Alternatives considered and rejected for now:** remote Agent2Agent server (adds auth/hosting/reliability burden), bespoke queue/database and agent chat folders (public sensitive data and merge noise), multiple agents editing shared contracts simultaneously, and automatic large context sharing. Revisit only after a demonstrated bottleneck and approval.

**Implementation refinement (Gemini CLI documentation):** a `.gemini/agents/*.md` custom subagent has YAML `name`, `description`, optional `model`, `tools`, `max_turns` and `timeout_mins`. Official [tools reference](https://geminicli.com/docs/reference/tools/) documents `read_file`, `grep_search`, `glob`, `list_directory`, `replace`, `write_file` and `run_shell_command`. A scoped coding agent with these tools can actually edit/tests *when a teammate starts the CLI and approves tool actions*, but its allowlist alone cannot enforce file ownership or prevent every risky shell command. Use per-worktree isolation, CLI human confirmations and the signed-off ASSIGN; never claim local test execution before it happens. Retain the independent read-only reviewer and avoid enabling remote agent communications.
